# 数据备份格式与迁移

`src/lib/data-backup.ts` 中的 `BACKUP_VERSION` 是备份数据结构版本，当前为 `3`。
它与 `appVersion` 独立：应用发布新版本时，不必递增备份版本；备份结构发生变化时，必须递增备份版本并提供迁移。

## 当前格式

JSON 顶层包含 `type: "anitabi-backup"`、整数 `version`、`appVersion`、`exportedAt` 和 `data`。
点击“导出备份”后，在 Sheet 中勾选收藏、巡礼计划、巡礼记录（含照片），默认三项均勾选，至少选择一项。
确认导出时先关闭 Sheet，再打开系统分享；取消或下滑关闭不会导出。
`data` 仅保存勾选类别的数据；未勾选类别的字段完全省略，不能用空数组代替。

- 收藏对应 `favoritePoints`。
- 巡礼计划对应 `plans` 和 `planListSortOrder`；两个字段必须同时存在或同时省略。
- 巡礼记录对应 `pilgrimageRecords`，其点位快照、日期、首次记录时间及照片身份独立于计划完成状态。

已勾选但没有数据的类别仍保存空数组，表示该类别的有效空备份。
计划保留 ID、名称、描述、时间、点位顺序、完成状态和信息快照，包括空计划。

`src/lib/data-backup-schema.ts` 显式定义 `DataBackupV1`、`DataBackupV2`、`DataBackupV3` 等文件格式类型。
这些历史类型必须保持不变，不能改为引用随应用演进的存储模型类型。
`BackupContents` 表示备份文件中实际包含的类别，`BackupData` 表示包含全部类别的本地状态。

例如，仅备份收藏时，`data` 为 `{ "favoritePoints": [...] }`；仅备份计划时，
`data` 为 `{ "plans": [...], "planListSortOrder": "desc" }`。

## 恢复流程

### 巡礼照片 ZIP

选择巡礼记录时，即使记录为空，也导出 ZIP；只选择收藏或计划仍导出 JSON。ZIP 中包括 `data.json` 和 `images/<照片文件名>`，图片保存真实字节，不使用 Base64。照片保留稳定 ID，设备内文件名可在恢复时重新分配。

```text
anitabi-backup-时间.zip
├─ data.json
└─ images/
   ├─ photo-xxx.jpg
   └─ photo-yyy.png
```

使用 fflate 的 `ZipPassThrough` 打包，图片保持 STORE 格式，逐文件以 256 KiB 块读取；已经压缩的 JPEG/PNG/WebP 不再重复压缩。恢复同样分块读取并直接写入临时文件，不把整个 ZIP 或全部图片读进 JS 内存。MVP 只接受本格式的 STORE ZIP，不接受改用 DEFLATE、ZIP64、加密、软链接或嵌套目录的 ZIP。

限制：JSON 元数据 20 MiB，ZIP 及解压后的总量 2 GiB，单张照片 128 MiB，最多 10000 个 ZIP 条目（含 `data.json`）。恢复前校验中央目录、路径、文件数量、实际大小、CRC32，以及声明照片与文件一一对应；缺图、额外文件、重复名字、路径穿越、截断或校验不符均拒绝恢复。带照片引用的裸 JSON 不作为完整备份接受。

巡礼记录照片的备份与恢复面向 Android/iOS 应用；Web 继续支持收藏和计划的 JSON 备份。

### 准备、确认和提交

1. 读取 JSON 或 ZIP，并检查文件大小、文件标识、元信息及版本是否有效；ZIP 图片先写入缓存暂存目录并完成校验。
2. 检查旧版本到当前版本的完整迁移路径。
3. 按 `1 → 2 → 3 …` 顺序迁移 `data`，保留文件原始 `appVersion` 和 `exportedAt`。
4. 严格校验迁移结果是否满足当前版本结构。
5. 展示文件实际包含的类别和恢复摘要，等待用户选择合并或覆盖，再写入存储。

恢复只处理文件中包含的类别，省略的类别不写存储、不发布到对应的状态仓库：

- 合并时按收藏点位 key、计划 ID 和计划内点位 key 去重，保留本地名称、描述、顺序和完成状态，仅追加新数据；计划列表排序偏好始终保留本地值。
- 覆盖时只替换包含的类别；仅恢复收藏不会改动计划，仅恢复计划不会改动收藏。包含计划时一并恢复其排序偏好。
- 包含某类别的空数组会在覆盖时清空该类别；省略该类别则保留原有数据。包含空计划备份时也会写入计划存储，防止重新生成首次安装示例计划。
- 巡礼记录合并按点位身份及 `dateKey` 归集，首次记录时间取较早值，照片按稳定 ID 去重，重复恢复不重复追加；独立导出产生的不同照片 ID 分别保留。
- 恢复照片仅写入应用文档目录，不再保存到系统相册。恢复记录不调用计划勾选操作，也不产生恢复当天的新记录。

所有需要的写入和回滚快照先准备完成，再同步写入存储；全部成功后才发布状态。
写入失败时回滚已尝试的步骤，包括发生异常的步骤，不发布成功状态。

照片先以唯一新文件名复制到应用图片目录，完整复制后再同步提交元数据，不会先覆盖或删除旧照片。复制期间发生的计划或收藏修改在提交前重新读取并参与合并。全部提交成功并发布状态后才清理不再引用的旧应用内照片；清理失败不会把已经成功的恢复误报为失败。

复制或元数据写入失败时清理本次新文件，保留原记录、原图片和系统相册照片。如果元数据回滚也失败，则保留本次新正式图片，避免存储中的残留引用指向被删除文件。记录写入、删除、图片导出备份和恢复共用串行锁，防止异步文件操作覆盖新记录。

无法读取损坏的本地记录时，禁止导出该类别和合并恢复；明确选择覆盖恢复仍可修复记录类别，其他未选类别不受影响。

迁移只发生在内存中，不修改原始文件和本地存储。
迁移函数会收到原数据的独立副本；迁移链缺失、函数抛出异常或结果无效时，恢复会在存储写入前停止。
更高版本的备份不会尝试降级；没有版本号的文件不会猜测版本。

## V1 兼容

V1 文件始终包含收藏、计划和计划列表排序偏好。导入时先按冻结的 V1 结构严格校验，
再通过 `1 → 2 → 3` 迁移，保留文件原始 `appVersion` 和 `exportedAt`。
缺少类别或其他结构错误的 V1 文件仍视为无效，不能按 V2 的局部备份解释。
迁移后的 V1 文件继续支持原有收藏、计划的合并与覆盖；V2 继续支持其类别选择规则。两种旧格式都省略巡礼记录，覆盖旧备份也不会清空现有巡礼记录。再次导出使用 V3 格式。
旧版应用不支持 V3 文件，需要升级后恢复。

## 新增结构版本

例如未来新增 V4 时：

1. 保留 V1、V2、V3 类型，新增 `DataBackupV4` 及所需类型。
2. 把 `BACKUP_VERSION` 改为 `4`，将 `DataBackup` 指向 V4，并更新当前结构校验和导出逻辑。
3. 保留 `1 → 2 → 3`，在 `BACKUP_MIGRATIONS` 注册 `3: migrateV3ToV4`。注册表的键是来源版本，每个函数只迁移到下一个版本。
4. 迁移函数接收 `unknown`，应先按历史结构校验，再转换字段。旧格式没有的新字段需要明确定义默认值；不能丢弃完成状态、时间、顺序、快照或空计划。
5. 增加真实旧版文件测试：通过 `parseDataBackup` 迁移后，分别验证合并、覆盖和重新导出。

新增版本时继续保留历史迁移链，无需为每个旧版本重新编写直达最新版的迁移。

测试同时覆盖真实 V1 文件迁移、单类别备份与恢复、空已选类别、局部写入及失败回滚。
`migrateBackupData` 的独立测试使用模拟结构验证多步转换、路径缺失、未来版本拒绝、迁移失败及源数据保护；模拟结构不代表应用的实际文件格式。
