# 数据备份格式与迁移

`src/lib/data-backup.ts` 中的 `BACKUP_VERSION` 是备份数据结构版本，当前为 `1`。
它与 `appVersion` 独立：应用发布新版本时，不必递增备份版本；备份结构发生变化时，必须递增备份版本并提供迁移。

## 当前格式

JSON 顶层包含 `type: "anitabi-backup"`、整数 `version`、`appVersion`、`exportedAt` 和 `data`。
`data` 保存所有收藏、巡礼计划及计划列表排序偏好。
计划保留 ID、名称、描述、时间、点位顺序、完成状态和信息快照，包括空计划。

`src/lib/data-backup-schema.ts` 显式定义 `DataBackupV1` 等文件格式类型。
这些历史类型必须保持不变，不能改为引用随应用演进的存储模型类型。

## 恢复流程

1. 读取 JSON，并检查文件大小、文件标识、元信息及版本是否有效。
2. 检查旧版本到当前版本的完整迁移路径。
3. 按 `1 → 2 → 3 …` 顺序迁移 `data`，保留文件原始 `appVersion` 和 `exportedAt`。
4. 严格校验迁移结果是否满足当前版本结构。
5. 展示恢复摘要，等待用户选择合并或覆盖，再写入存储。

迁移只发生在内存中，不修改原始文件和本地存储。
迁移函数会收到原数据的独立副本；迁移链缺失、函数抛出异常或结果无效时，恢复会在存储写入前停止。
更高版本的备份不会尝试降级；没有版本号的文件不会猜测版本。
当前版本为第一个格式版本，因此迁移注册表为空，现有 V1 文件直接进行结构校验。

## 新增结构版本

例如未来新增 V2 时：

1. 保留 V1 类型，新增 `DataBackupV2` 及所需类型。
2. 把 `BACKUP_VERSION` 改为 `2`，将 `DataBackup` 指向 V2，并更新当前结构校验和导出逻辑。
3. 在 `BACKUP_MIGRATIONS` 注册 `1: migrateV1ToV2`。注册表的键是来源版本，每个函数只迁移到下一个版本。
4. 迁移函数接收 `unknown`，应先按历史结构校验，再转换字段。旧格式没有的新字段需要明确定义默认值；不能丢弃完成状态、时间、顺序、快照或空计划。
5. 增加真实旧版文件测试：通过 `parseDataBackup` 迁移后，分别验证合并、覆盖和重新导出。

新增 V3 时，继续保留 `1 → 2`，追加 `2 → 3`，无需为每个旧版本重新编写直达最新版的迁移。

当前 `migrateBackupData` 的测试使用模拟 V2/V3 结构验证多步转换、路径缺失、未来版本拒绝、迁移失败及源数据保护，不代表应用已经发布了 V2/V3。
