# 地图数据刷新与分片恢复

地图数据来自 `g.json` 及其对应的 `g{n}.json` 详情分片。刷新流程由 [map-data.ts](../../src/services/map-data.ts) 管理，[map-data-schema.ts](../../src/services/map-data-schema.ts) 校验数据，[map-storage.ts](../../src/lib/map-storage.ts) 维护缓存，[use-map-data.ts](../../src/store/use-map-data.ts) 发布页面状态。

## 完整缓存与下载暂存

完整缓存与正在下载的分片分别存储，只有全部分片通过校验、提交前索引复核通过后，才能写入新的完整缓存。

| 记录       | MMKV key                       | 用途                                                                                  |
| ---------- | ------------------------------ | ------------------------------------------------------------------------------------- |
| 完整缓存   | `assembled-data-v2`            | 单条记录保存 `schemaVersion: 2`、远端版本和组装结果，避免版本先更新、数据尚未完整写入 |
| 下载清单   | `map-detail-manifest-v1`       | 保存本轮下载的 revision                                                               |
| 分片暂存   | `map-detail-v1:<index>`        | 保存通过校验的原始详情和对应 revision                                                 |
| 旧格式缓存 | `assembled-data`、`g-modified` | 兼容升级前数据，完整迁移成功后清理                                                    |

revision 由远端 `modified`、分片容量 `batchSize` 和按索引顺序排列的作品 ID 组成。分片数量按 `ceil(作品数 / batchSize)` 计算。远端版本、容量或作品顺序变化时，旧暂存失效，重新下载当前索引需要的分片。

每个分片必须包含它负责的全部作品，以及索引声明的点位 ID。重复、缺失或意外的作品、缺失点位和不合法结构会作为下载失败处理。作品允许没有点位；有合法作品详情但点位数组为空、索引中使用空 metadata 哨兵，不等于缺片。

旧格式曾可能在分片失败后仍写入新版本，因此只用它先展示地图，不信任独立的 `g-modified` 来跳过下载。首次读取旧格式时保留原有可浏览数据，同时设置 `isPartial: true` 表示完整性待确认；重验失败仍保留这些数据。首次成功重验后一次发布完整新数据，设置 `isPartial: false` 并写入新格式，之后同版本且内容覆盖当前索引的完整缓存可跳过详情下载。这里的“单次重验”指一次成功迁移，失败后仍可重试。

分片暂存只用于下载恢复，不作为页面数据源。首载、手动重试和后台刷新都不会逐片发布作品或更新地图 GeoJSON；全部分片通过校验、提交前索引复核通过后，才一次更新页面数据。已有缓存可继续显示；没有缓存时只展示加载进度，避免下载期间反复重建地图数据。

完整缓存采用首次读取后保留对象快照的方式，服务继续在启动阶段按需加载，避免反复解析大 JSON 或提前增加开屏工作。

## 请求、重试与提交

1. 获取并校验 `g.json`，读取当前版本、分片容量与作品列表。
2. 若已有可验证的同版本完整缓存，直接返回；否则准备对应 revision 的下载清单。
3. 读取暂存分片并再次校验，只请求缺失或损坏的分片。
4. 最多启动 3 个分片下载 worker。每个请求最多尝试 3 次，即首次请求加最多 2 次额外重试；单次超时为 30 秒。
5. 分片全部成功后重新读取 `g.json`，核对 revision 与完整作品列表，再提交完整缓存并清理旧格式和暂存。页面只接收本轮最终的完整结果。

可恢复的网络错误、HTTP 408/429/5xx、解析或结构校验错误会重试；取消和其他 HTTP 4xx 不重试。两次退避使用 `500ms × 2^attempt × (0.5 + 随机数)`，分别约为 250–750ms 和 500–1500ms。重试耗尽后服务抛出包含失败分片编号的 `MapDataDownloadError`，不会把部分结果提交为完整缓存。

索引与详情分片请求传入 `suppressErrorToast: true`，避免每个分片和每次重试反复弹出网络错误。首载和旧格式缓存重验通过首页加载状态反馈；已有完整可信数据时的更新走静默恢复，不把刷新错误展示到页面。`FetchProgress.batch` 表示已完成的分片数，`total` 表示总分片数；分片乱序返回不会让完成数倒退。

初次和提交前的索引请求均添加独立的缓存绕过参数；详情请求带远端版本参数，重试时再增加缓存绕过参数。具体拼接见 [api.ts](../../src/services/api.ts)。这些查询参数用于降低 CDN 返回旧内容的概率。

上游详情地址不是不可变的版本化资源，也没有提供每片内容摘要。最终索引复核能发现下载期间可见的索引变化，但不能证明 CDN 与全部分片绝对属于同一时刻的快照。若复核发现变化，本轮不提交完整缓存，保留旧完整数据与暂存；下次加载按新索引决定哪些暂存失效。

## 页面状态与恢复

本次新增的统一加载、失败、暂停提示和手动重试入口仅放在首页左上角，用于尚无完整数据的首载，以及旧格式缓存完整性待确认的重验。已有完整可信数据时，后续更新保持静默。下表中的提示与操作均指首页；store 状态供其他页面继续沿用原有加载、内容或错误流程。

| 场景                       | 页面与 store 行为                                                                          |
| -------------------------- | ------------------------------------------------------------------------------------------ |
| 首次加载，分片尚未全部完成 | `data: null`、`status: loading`，只更新加载进度，不发布成功分片                            |
| 首次加载，任一分片最终失败 | `data: null`、`status: error`，展示错误和重试入口；成功分片保留在暂存中供重试复用          |
| 有完整可信数据，更新失败   | 保留旧地图，`status: ready`，`progress` 和 `error` 均为 `null`；前台按退避计划自动重试     |
| 旧格式缓存完整性待确认     | 保留原地图，`status: ready`、`isPartial: true`；重验失败仍显示原有错误和手动重试入口       |
| 全部分片及最终索引复核成功 | 一次发布完整新地图，`isPartial: false`；缓存保存成功后清除错误并重置外层重试退避           |
| 首载或旧缓存重验写盘失败   | 完整新地图仍可在本次运行中使用，`isPartial: false`；提示“地点已加载，但未能保存供下次使用” |
| 静默更新的新缓存写盘失败   | 本次完整网络结果仍可浏览，`progress` 和 `error` 保持 `null`，安排静默重试保存              |
| 首载或重验中清缓存         | 保留原有 `data`，结束刷新；通过 error progress 提示“加载已暂停，可重试继续”，保留重试入口  |
| 静默更新中清缓存           | 保留原有 `data`，取消在途更新、重试计时及自动恢复意图，不自动重新填充缓存                  |

加载进行时 `isRefreshing: true`，结束、失败或取消后归为 `false`。`ready` 表示当前有可用数据；`isPartial: true` 只表示旧格式缓存完整性尚未确认，不表示下载过程中已向页面发布部分分片。是否存在刷新或保存问题还需要检查 `error` 与 `progress`。

首载和旧格式缓存重验期间，首页左上角的加载提示卡片显示加载进度、最终错误、暂停状态与重试按钮。搜索、收藏、计划导入、批量浏览和相机页面不新增统一状态提示或提示布局，继续保留原有内容及原有加载、错误流程。计划地图原本使用的 `LoadingBadge` 继续沿用，不为其新增重试交互；批量浏览原有的错误和重试入口保留。

数据完整性约束不因提示范围缩小而改变。旧格式缓存完整性待确认时，导入页面保留待导入计划，等待完整数据，不能把尚未确认的缺失点位直接作为已移除点位导入。

首页新增的重试入口和批量浏览原有的重试入口都调用同一个 `initialize()`。同一缓存 generation 的有效并发调用共用一次加载任务。手动重试保留当前可浏览地图，复用同 revision 下已验证的成功分片，只下载缺失或损坏部分；成功分片不会提前更新页面或 GeoJSON。首载和旧缓存重验的可恢复失败由首页重试进度反馈，耗尽本轮尝试后再显示最终错误与操作入口，不为每次失败重复弹出 Toast。

是否静默取决于本轮开始时是否已有完整可信的数据。首载或旧缓存重验即使最终取得完整网络结果，本轮保存失败仍按上述可见流程提示；这个完整结果可继续在内存中使用，之后以它为基准发起的更新可走静默流程。

成功暂存写入 MMKV 后可跨应用重启复用。重启仍需先取得远端索引确认 revision，再读取对应分片；这不等于未完成下载可以在完全离线时恢复浏览。暂存清单或某片 JSON 损坏时按缓存缺失处理，重新拉取相应数据，不将损坏记录升级为完整缓存。暂存保存失败时，当前运行仍可复用内存中的分片，但跨重启恢复不作保证。

完整缓存把远端版本和结果放在同一条记录中，提交后读回核对；提交失败会尝试恢复先前记录，内存中的已验证正式缓存版本不提前推进。回滚或底层存储本身持续失败仍可能影响下次启动。页面保留本次完整网络结果；首载或旧缓存重验提示保存失败，静默更新则安排自动重试，均不能将内存中可用解释为持久化已成功。

## 完整数据的静默更新与前后台

已有完整可信数据时，刷新失败或新完整缓存写入失败都保留可用数据，不向页面发布失败 `progress` 或 `error`，也不弹出错误 Toast。本轮内部的请求策略仍是最多 3 次尝试、每次 30 秒超时；该策略耗尽后，外层以整个刷新轮次为单位恢复：第一次等待 30 秒，之后等待 120 秒，再之后每次最多等待 300 秒。每轮完整成功会重置退避，后续失败重新从 30 秒开始；缓存保存失败仍算需要恢复。

静默更新仅在 `AppState` 为 `active` 时开始。`inactive`、`background` 和初始 `null` 等未知状态不会触发静默请求。外层等待只累计前台停留时间：离开前台时清除计时器并保存剩余延迟，返回前台后继续倒计时；若离开前台打断了正在进行的静默刷新，取消该轮在途请求，保留已验证的暂存分片，回到前台后立即发起恢复轮次。

服务支持 `refreshMapData(cachedData, onProgress?, { signal })`。调用方取消通过本轮 `AbortController` 中止索引、分片及请求重试退避；不会推进缓存 generation，也不会清理成功暂存。即使底层请求忽略取消，迟到响应也不得写入暂存、提交完整缓存或向页面发布结果。请求和退避的取消监听在本轮收尾时释放。

本流程使用前台生命周期和计时恢复，不实时监听设备网络是否重新连接，也不保证刚恢复联网就立即请求。前后台暂停只针对静默更新；无缓存首载及旧格式缓存重验保留原有加载、失败和手动重试行为。

## 清缓存与在途任务

`clearMapCache()` 先增加内存中的 generation，再清除完整缓存、旧格式和暂存。旧任务即使稍后收到网络响应，也不能写回分片或完整缓存；服务以 `MapDataCancelledError`（`name: AbortError`）结束失效工作。

刷新任务订阅缓存失效事件，为索引和分片请求传入同一 `AbortController.signal`；清缓存时主动 abort 在途 HTTP 请求。generation 检查继续防止取消竞态或迟到响应写回，组成请求取消与结果失效的双重保护。

store 同时检查任务身份、调用方取消状态和 generation，忽略旧任务迟到的进度、结果与错误，旧任务的收尾也不能清掉新任务的状态。清缓存保留本次运行中已经显示的地图，同时取消静默重试计时器和回前台后的恢复意图，不自动重建刚清除的缓存。

若清缓存取消的是首载或旧缓存重验，则结束刷新并发布“加载已暂停，可重试继续”的 error progress，首页继续显示暂停提示和手动重试入口。首次尚无数据时也能回到首页直接重试。若取消的是已有完整数据的静默更新，则静默结束，页面继续显示旧数据。显式重新加载使用新的 generation；如果新任务已经开始，旧任务不得覆盖它的状态。

根布局拥有前后台订阅。布局卸载时取消生命周期和缓存失效监听、计时器以及本轮在途请求，清除恢复意图；卸载后的迟到结果不发布到 store。

删除失败会向调用方报告，同时仍使旧 generation 失效，并尽力清理其他记录。清理失败时不能声称所有磁盘缓存均已删除。

## 验证与设备验收

相关 Node 回归测试已通过 `test:map-data` 接入 CI：

```bash
yarn test:map-data
```

- `map-data-schema.test.mjs`：索引与分片校验、作品及点位缺失、重复记录和合法空数据。
- `map-storage.test.mjs`：完整缓存提交、旧格式兼容、暂存复用、存储故障、回滚与清缓存失效。
- `map-data.test.mjs`：真实 service、storage 和 Zustand store 的重试、恢复、乱序进度、完整结果一次发布、旧缓存保留、调用方取消及 generation 竞态；网络和原生存储使用 mock，重试退避不真实等待。
- `map-data-retry.test.mjs`：完整缓存的静默重试、前台退避、后台暂停、清缓存、手动重试和卸载竞态；使用可控时钟及 AppState。
- `map-root-lifecycle.test.mjs`：根布局的生命周期订阅、启动顺序、卸载后的迟到回调及 StrictMode 下的初始化。
- `map-data-request.test.mjs`：真实 API、请求处理器与错误拦截器的配置透传、动态缓存参数、静默错误和其他请求原有 Toast 反馈；HTTP transport 使用 mock，不访问真实网络。
- `map-loading-badge.test.mjs`：首页进度条的尺寸约束、百分比填充、真实总数和错误重试状态。

- `map-data-consumers.test.mjs`：旧缓存完整性待确认时的导入守卫及页面消费行为。
- `plan-point-batch-browser.test.mjs`：批量浏览继续使用可用缓存，并保留查询、返回和分组选择行为。

Node 测试只验证受控输入下的业务和状态顺序，不证明设备网络、真实 MMKV、Mapbox 渲染或交互已通过。真机仍需验收：

1. 首次加载期间断网，确认未完成的分片结果不出现在地图或列表；最终失败后首页展示错误与重试入口，不生成“已完成”的空地图，其他页面不新增统一提示。
2. 恢复网络后从首页重试，仅补齐缺失分片，观察进度和最终一次地图更新；连续点击重试不应重复发起一轮下载，也不应重复弹出中间失败 Toast。
3. 部分下载后退出并重新启动，联网后确认同版本暂存复用，但完整完成前仍不逐片展示；有完整可信缓存时离线启动仍显示旧地图，刷新失败保持静默并安排前台重试。
4. 分别在首个分片成功前和部分分片已暂存后清缓存，回到首页确认暂停提示与重试按钮仍可用；重试可恢复，旧响应不会重新填充缓存或覆盖新任务的状态。
5. 验证实际 HTTP 超时、弱网重试时长，以及前后台切换和系统结束进程后的恢复边界。
6. 模拟空间不足或存储失败，确认完整网络结果仍能浏览；首载或旧缓存重验提示保存失败，已有完整数据的静默更新保持安静并自动重试，重启后不误认为完整缓存已经更新。
7. 观察完整可信数据的静默失败按前台时长依次等待 30 秒、120 秒、300 秒，成功后退避重置；后台不消耗剩余等待，回到前台能继续，取消在途更新后能复用暂存。
8. 静默等待或更新期间主动清缓存，确认不会因计时器或回前台自动重建；卸载根布局后不留下生命周期监听、计时器或在途刷新。
