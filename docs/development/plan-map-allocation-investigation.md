# 大计划反复进入地图的分配排查

记录日期：2026-10-17。状态：已定位并优化一个随点位数增长的 ART 分配热点，修复效果待用户构建后验收。

## 点位数量对照

使用已安装的 `58eb154` x86_64 Release 诊断包，在 MuMu Android 15 上采集 ART allocation
sampling，间隔为 65,536 字节。各计划使用同一个首点，从首张卡片进入地图，快速返回并再次进入，
每档完成 12 次原生地图创建与销毁；返回后不等待上一张地图销毁才再次点击。

| 实际有效点位 | ICU Collator 对象抽样命中数 | 首次卡片点击尝试到原生 Surface 初始化，中位／P95 |
| -----------: | --------------------------: | -----------------------------------------------: |
|            1 |                           0 |                                      153／319 ms |
|         1011 |                        3721 |                                      295／706 ms |
|         2998 |                       11396 |                                      558／692 ms |
|         4998 |                       18526 |                                     864／1146 ms |

3000／5000 点导入文件各有 2 个点未被设备当前地图数据匹配，表中记录界面显示的实际点数。
四档追踪均无采样错误或数据丢失。追踪包含不同长度的空闲尾段，表中均有完整的 12 轮操作。

这些命中数是未加权的已采样对象数，不是全部对象数或 Java 总分配量。Surface 初始化时间含采样开销、
路由转场和重试，P95 使用 12 轮的 nearest-rank，不能作为可交互时间或手机冻结时长。
模拟器的循环结束后仍能打开列表设置，未直接复现手机上数秒的停顿。

调用栈中随点数增长的是 Hermes Intl.Collator → ICU CollationSettings.clone。
Fabric 属性导入的大字符串也随点数近乎同比增长，推测来自全量点位 GeoJSON；通用调用栈不能确认具体属性。
同一选中点的位图复制样本数为 32／32／36／32，基本固定。

## 本次修改及历史意图

`fbe833a2` 引入与计划排列顺序无关的点位成员键，让完成状态或拖动排序变化时复用地图点位数据。
原实现用 `pointId.localeCompare` 排序，每次重新进入地图都会重复创建比较期间的 Java ICU 对象。

成员键现改为按数字作品 ID、字符串点位 ID 的代码单元排序。该键只用于组件内的成员比较，
点位 ID 无需语言排序；实际番剧与点位显示顺序仍由原始数据、`plan.items` 决定。
完成状态与重排继续得到相同成员键，增加、移除或更换点位会更新键；键不落盘。

定向测试覆盖重排、完成状态、成员变化、5000 个含 Unicode 的 ID 及输入不被修改。
类型检查、定向 ESLint 与格式检查通过；未构建新安装包，因此尚无修复后的 Android 分配或耗时数据。

## 后续验收边界

用户在本分支构建后，以相同计划从顶部入口及卡片入口分别快速进出至少 12 轮，确认停顿是否改善，
并检查地图操作、返回、完成状态和拖动顺序。若仍有停顿，继续采集无高频 `dumpsys meminfo` 干扰的日志。
