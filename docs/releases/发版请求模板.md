# Anitabi 发版请求模板

下次发版时，复制第一段发送。先审核 GitHub Release 说明、App 短文案及可选的旧客户端升级摘要；审核通过后，再复制第二段授权本次发布。将方括号内的内容替换为实际信息，不适用的项目可写「无」。

## 第一步：准备发版，审核文案

```text
请帮我准备 Anitabi 的 GitHub Release 整包发版，先停在文案审核阶段。

目标版本：[例如 v0.6.0；若未确定，请检查当前版本并建议]
发布渠道：[production 正式版 / preview 预览版]
发布平台：[Android APK + iOS IPA；如仅需 Android，请写明]
本次变更：
- [新增或调整的功能]
- [修复的问题]
- [需要告知用户的其他变化]

更新重要程度：[major 重点更新 / normal 普通更新]。由我手动指定，不根据版本号推断。
是否强制更新：[否 / 是；若是，说明适用的最低版本或构建号及原因]。
旧客户端跨版本摘要：[不需要，默认只展示本次更新 / 需要，请说明希望强调的旧功能；由你起草供我审核]
文案语言及特别要求：[默认中文；其他要求写在这里]

请核对待发布的代码、版本号、现有发版流程和工作区改动；准备本次版本的 GitHub Release 详细说明、App 弹窗短文案，以及对应的重要程度元数据。App 短文案只写本次版本的变化。旧客户端默认也只看本次短文案；若我指定需要跨版本摘要，请另写一份包含本次变化和人工挑选的旧版重点的文案，不要自动拼接全部历史重大更新。保留所有无关的工作区改动，只处理本次发版相关文件。

请完成适当的静态检查，然后把 GitHub Release 说明、App 短文案和可选的旧客户端升级摘要的完整内容，以及版本和渠道、major/normal 标记、强制更新设置、拟提交文件、检查结果及实际发布步骤展示给我审核。请举出两个不同已安装版本的弹窗展示例子，确认新版客户端最多展示本次版本和最近一次尚未安装的重大更新。请核对发版入口是否支持本次强制更新设置；如果信息不足，列出需要我决定的具体事项。

此阶段不要提交或推送、创建 tag、运行构建或打包、触发 GitHub Actions、创建 GitHub Release、发布 EAS Update，或修改远端更新清单。等我明确批准文案并单独授权本次发布后再继续。仅回复「文案通过」不代表发布授权。
```

## 第二步：审核通过后，授权本次发布

确认全部文案无误后，复制下面这段作为回复。若需修改文案，先直接提出修改意见，待再次审核后再发送授权。

```text
我已审核并批准 [版本号] 的 GitHub Release 详细说明、App 弹窗短文案，以及 [不使用旧客户端跨版本摘要 / 已审核的旧客户端跨版本摘要]。更新重要程度为 [major / normal]，强制更新设置为 [否 / 具体规则]。

我授权你在本次任务中提交并推送本次发版相关改动，按已经确认的 [production / preview] 发版入口触发本次构建和 GitHub Release 发布，并核对构建产物与对应更新清单。使用 tag 触发时可创建并推送对应 tag；如果本次设置强制更新，请使用支持相关参数的手动工作流，不要预先创建同名 tag。请使用与审核稿一致的文案，保留无关的工作区改动；若文案、版本或发布范围需要变化，先交给我重新审核。

[本次是否还要单独发布 EAS Update：否；如需要，请明确写明渠道和内容。]
```

`major` 用于挑选用户尚未安装的最近一次重大更新，弹窗不会自动列出全部历史重大更新；强制安装由 `mandatory`、最低支持版本或构建号单独控制。正式版的双平台 tag 发版入口是 `Mobile Release`；不要同时触发 Android-only 工作流。
